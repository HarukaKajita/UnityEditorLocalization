# Unity 公式の UI 用語に合わせる（2026-08-09 制定）

## 何を決めた規則か

**Unity が公式にエディタ UI をローカライズしている言語では、公式訳をそのまま使う。**
対象は **ja / ko / zh-Hans / zh-Hant の 4 言語**（Unity Hub の言語モジュール。Unity 2022.3 と
Unity 6 のどちらも同じ 4 言語。ほかの言語はエディタ UI のローカライズ自体が存在しない）。

理由は「公式が正しいから」ではなく、**読み手が見ている画面がそれだから**である。
エディタ拡張の文言は Unity のウィンドウの中に、Unity 自身の文言と隣り合って表示される。
そこで語が割れると、購入者は同じ画面で 1 つの概念の 2 つの呼び名を同時に読むことになる。

## エディタ UI とドキュメントで訳語が割れている場合

**エディタ UI を優先する（2026-08-09 ユーザー決定）。** 開発者が頻繁に目にするのはエディタだからである。

これは机上の話ではない。**簡体字の「Asset」で実際に割れている**（実測 2026-08-09）:

| Unity の面 | 訳語 | 実測 |
|---|---|---|
| **エディタ UI**（言語モジュールの `.po`） | **`资产`** | 2022.3 で 245:45、Unity 6 で 289:43。`msgid "Asset"` 単体も `资产`、`Delete selected asset?` → `删除选定资产？` |
| 公式ドキュメント（简体中文） | `资源` | Asset 関連ページで `资产` は **0 件** |

繁体字は逆に、エディタ UI が `資源` で一貫している（302:0）。**「簡体字が `资产` なら繁体字も `資產`」
という推測は誤り。**必ずロケールごとに実データを見る。

## 実測で見つかった誤用（この規則を作る動機になった事例）

2026-08-09 に 5 リポジトリのカタログを公式訳と突き合わせた結果:

| ロケール | 語 | 使っていた語 | 公式 | 件数 |
|---|---|---|---|---|
| zh-Hans | Asset | `资源` | `资产` | 61（4 リポジトリ全部） |
| zh-Hant | Asset | `資產` | `資源` | 23（EPE / UEL / TAE。UMPD だけ正しかった） |
| zh-Hant | Texture | `紋理` | `貼圖` | 23（TAE / UMPD）。`紋理` は簡体字圏の語 |
| ja | Asset | `資産` | `アセット` | 1 |
| ko | Sub-asset | `서브에셋` | `서브 에셋`（分かち書きあり） | 12 |

**同じ組織の別リポジトリ同士でも割れていた**点に注意する（zh-Hant の Asset は 3 対 1 で割れていた）。
1 つのリポジトリだけを見ても気付けないので、**用語の検査はリポジトリを横断して行う**。

## 使い方

```bash
# 対照表と突き合わせる（公式ローカライズのある 4 言語だけを見る）
python3 scripts/check_unity_official_terms.py path/to/Locales
```

対照表の正本は同じフォルダの `unity-official-terms.json`。

- `official` … その語の公式訳。Unity 2022.3 の言語モジュールの `.po` から、
  **msgid が語そのものと完全一致するエントリ**を抽出して作った。
- `knownWrong` … **実測で確認した誤用だけ**を載せる。

**`knownWrong` に「他ロケールの公式訳」を機械的に流し込んではいけない。** 一度そうしたところ、
出た 5 件が**全部偽陽性**だった（実測 2026-08-09）:

| 検出 | 実際 |
|---|---|
| zh-Hant の `文件`（File の zh-Hans 公式訳と同形） | `開啟線上文件`＝「オンライン**文書**を開く」。正しい |
| ja の `複製`（Copy の zh-Hant 公式訳と同形） | `境界を複製`＝replicate。正しい |
| ja の `属性`（Property の zh-Hans 公式訳と同形） | ShaderLab の**属性**（`[UberToggle]`）。正しい |

漢字圏では「他の言語の正解」が「この言語の別の正しい語」と一致してしまう。
**候補は実際に踏んだ誤用から 1 件ずつ育てる。**

## この検査の限界

- **明らかな取り違えの検出器であって、承認器ではない。** 対照表に無い語は何も言わない。
- 鳴った箇所が本当に Unity の概念を指しているかは人が読む（上表の `文件` のような例外がある）。
- **公式ローカライズが無い 15 言語は守備範囲外。** それらは SKILL.md「証拠の序列」に従って
  コミュニティの慣用で決める。

## Transform 系の一般語を足した（2026-08-26 実測）

MiscPack の整列コンポーネントで、`Local`（ローカル位置を 0 に戻す）の訳が決められずに止まった。
当時の対照表は Asset〜Window の 43 語で、**Transform 周辺の基本語が 1 語も入っていなかった**。
そこで 4 言語 × 35 語を一次資料から調べ直した。**調べた 35 語のうち、対照表（`terms`）へ入れたのは
横断検証を通った 13 語だけ**である（下記「反映した語と、保留した語」）。調べた語:

Local / Global / World / Reset / Position / Rotation / Scale / Parent / Child / Children /
Origin / Pivot / Transform / Axis / Grid / Cell / Row / Column / Spacing / Offset / Target /
Order / Preview / Gizmo / Play Mode / Undo / Default / Index / Radius / Angle / Direction /
Anchor / Interpolation / Space / Enabled

### 反映した語と、保留した語

**`terms` に入れた 13 語**（`evidence` フィールドで出所を持つ）:
Row / Column / Reset / Target / Default / Undo / Enabled / Angle / Global / Play Mode /
Position / Rotation / Axis

**保留した 22 語**とその理由:

| 保留の理由 | 語 |
|---|---|
| zh-Hant 側に Unity 出荷物の実測が無い（人手記事のみ） | Local / Cell / Origin / Anchor / Pivot / Gizmo / Spacing / Offset / Radius / Interpolation |
| 語義が文脈で三分する（座標空間 / 設定スコープ / 余白） | Space |
| Unity 出荷物の証拠が値と食い違う（`上層` / `下層`） | Parent / Child / Children |
| 既存 43 語に `.po` 由来で入っており値も一致（二重定義を避ける） | Preview |
| 6 リポジトリで実使用 0 件のため突き合わせができない | World / Grid / Index / Direction / Transform / Order |

**保留した語は「訳が分からない」ではなく「対照表として強制するだけの証拠が無い」という意味である。**
カタログ側は現状維持でよい。`.po` を実測できたら格上げする。

#### 最重要の 1 件: 繁簡で row / column の対応が入れ替わる

| | row | column |
|---|---|---|
| zh-Hans（大陸） | `行` | `列` |
| **zh-Hant（台湾）** | **`列`** | **`欄`** |

**zh-Hans を字体変換して zh-Hant を作ると必ず取り違える。** zh-Hant は Unity 出荷物で実測済み
（Unity Hub zh-TW の `PROJECT_TABLE_ROW_ARIA_LABEL` = 「…的專案列」、Plastic zh-Hant の
`EditorOptionsColumnGuides` = `欄輔助線`）。レビューで「zh-Hans と揃っていない」と見えても直さないこと。
zh-Hant の `欄位` は field の意味でも使うので、機械置換は禁止。

### 証拠の等級（重要）

**この 35 語は Tier 2（公式ローカライズ版ドキュメント）で確定した。Tier 1（言語モジュールの `.po`）は未実測。**
検証機（`C:\UnityEditors` の 2022.3.22f1 / 6000.0.60f1 / 6000.3.5f1）に言語モジュールが入っておらず、
Unity Hub のキャッシュにも `.po` が無かった。既存 43 語は `.po` 実測なので、**同じ表の中に等級の違う行が混ざる。**

- `.po` を実測できたら、**エディタ UI の訳を優先して上書きする**（エディタとドキュメントは実際に割れる。
  簡体字の Asset が `资产`（エディタ）と `资源`（ドキュメント）で割れていた前例がある）。
- 上書きするときは**カタログ側も同時に直す**。片方だけ直すと家の中で割れる。

### 調べて分かった、この 4 言語の性格

- **繁體中文には Unity 公式のドキュメントが無い。** 公式ローカライズはエディタ UI だけなので、
  `.po` を取れない限り繁體中文は Tier 2 の証拠が原理的に存在しない。台湾の実例（Tier 4）で補うことになる。
- **2022.3 の簡体字マニュアルは全訳ではない。** ページによって本文が英語のまま残る。
  訳語を採るときは、その語が実際に中国語で書かれている箇所を選ぶこと。
- 韓国語マニュアルは実在する（`docs.unity3d.com/kr/2022.3/Manual/`）。

### 出典の作法（2026-08-26 に実際に踏んだ事故から）

- **未翻訳の英語段落を出典にしない。** 公式ローカライズ版のページでも、段落単位で英語のまま残る。
  そこを「公式訳」として引くと、**英語を訳し戻したものが公式訳として記録される**（実測: zh-Hans の
  `Scale` で 1 件発生し、横断検証で捕まった）。引用はその言語で書かれている箇所からだけ採る。
- **`docs.unity3d.com/cn/2022.3/` の Manual は翻訳されていない。** 見出しと一部の語だけ中国語で、
  本文・属性表は英語のまま。**完全翻訳された最後の CN Manual は 2019.4〜2021.3**。簡体字の証拠は
  この版から採る（ScriptReference も `/cn/2019.4/` は翻訳済み）。
- **韓国語マニュアルは Inspector のプロパティ名・ボタン名を英語太字のまま残す**方針（Position /
  Rotation / Scale / Reset が実例）。**UI ラベルそのものの韓国語は docs から取れない**ので、
  説明文の語彙を採るしかない。ko の confidence が上がりにくい構造的な理由である。
- **取得層（WebFetch 等）の整形が引用へ混ざる。** markdown の `**` 付与、表セル境界の ` - ` 挿入、
  Glossary 見出しの書き換え、版番号の脱落を実測した（253 件中 16 件）。**生 HTML を取ってタグを
  落とし、逐語で入れる。** 要約経由の引用は、内容が合っていても後から grep で照合できない。
- **`WebFetch` は原文に無い引用を返すことがある。** 実測 2 件（存在しない「原点に戻す」、英語のみの
  ページに対する中国語の作文）。**争点の語は必ず逐語で取り直す。**
- **403 を返す出典**（例: `ithelp.ithome.com.tw`）は、引用に加えて取得日時と取得手段を残す。
  後から機械監査できないので、tier 4 の個人記事だけに依存する語は対照表へ載せない。
- **`catalogUsage` には突き合わせた commit hash と件数の単位を書く。** 未コミットの作業ツリーで
  数えると結論が腐る（実測: 03:33 に数えた `本地` 4 件は、03:49 のコミットでは `局部` 5 件だった）。
  件数は「キー本数（出現回数）」の形にし、数えた対象（`Packages/` 配下の正本のみ、
  `Library/PackageCache` は除外）も添える。

## 家の用語（familyTerms）— 公式訳とわざと違える語

**公式訳に揃えるべきでない語がある。** kajitaharuka の 6 リポジトリは、次の語について
Unity 公式訳とは違う語を意図的に使っている。理由が無いと後の担当者が「公式に揃える」と称して
壊してしまうので、対照表の `familyTerms` に理由つきで持たせ、**検査スクリプトが逆向きに守る**
（`avoid` に挙げた語を使っていると指摘する）。

| 語 | 公式訳 | 家の用語 | わざと違える理由 |
|---|---|---|---|
| Target | ja `ターゲット` / ko `타겟` | ja `対象` / ko `대상` | 指しているのは Build Target のような Unity の固有機能名ではなく「操作の対象」。6 リポジトリ 46 件が `対象` で一貫している |
| Default | ja `デフォルト` | ja `既定` | 日本語 IT 文書の標準表記。4 リポジトリ 22 件（UEL 11・UEWCE 5・MiscPack 3・TAE 3）が `既定`、`デフォルト` は 0 件。EPE / UMPD には当該概念の用例が無い |
| Index | ja `インデックス` / zh-Hans `索引` | ja `要素番号` / zh-Hans `序号` | 利用者が数える「何番目か」であり、配列の添字という実装語ではない |
| Origin / Anchor | ja `原点` / `アンカー` | ja `基準点` / `基準点の位置` | 原文（`ja`）が `基準点` で、Unity の Origin フィールドとは別概念。訳は原文に従う |
| Grid | ja `グリッド` | ja `格子` | 整列の形を指す普通名詞として使っており、Unity の Grid コンポーネントを指していない |
| Play Mode | ja `再生モード` | `Play Mode`（原語のまま） | 全 19 ロケールで原語維持と決めた識別子。UI 上の場所を一意に指すため |
| Rotation / Direction | ja `回転` / `方向` | 文脈で `向き` と使い分け | `回転`＝回転量（度）、`向き`＝どちらを向くか。同じ画面に両方が出るので分けている |

**この表に足すときは理由を必ず書く。** 理由の無い逸脱は、ただの用語割れと見分けがつかない。

## 言語モジュールが無い機でも Unity 公式訳は取れる（2026-08-26 発見）

`.po`（言語モジュール）が入っていない機は珍しくない。**入れ直さなくても、Unity が出荷している
別の公式ローカライズ資産から同じ語を取れる。**繁體中文の調査で実際に使えた経路を、強い順に挙げる。

| 経路 | 場所 | 実測 |
|---|---|---|
| **Unity Hub の locale バンドル** | `C:\Program Files\Unity Hub\resources\app.asar` の中の `/.vite/build/zh_tw-*.js`（言語ごとに 1 ファイル） | en 2,922 キーと対応付けられた。`common.RESET` = `重設`、`Sort by target platform` = `依目標平台排序`。既存の対照表（`Asset` = `資源`）とも一致し、資料として妥当だと確認できた |
| **Unity 公式パッケージ同梱の .po** | `com.unity.learn.iet-framework` / `.authoring` の `Localization/*.po`（npm キャッシュや PackageCache 内） | zh-hant で msgid 85 件。多くは未訳のまま残るので、訳が入っている行だけ使う |
| Unity 公式ドキュメントのローカライズ版 | `docs.unity3d.com/ja|cn|kr/<version>/Manual/` | 繁體中文版は**存在しない**。2022.3 の简体中文版はページによって本文が英語のまま残る |

`asar` は tar 相当のアーカイブなので、`node` で `app.asar` のヘッダを読めば個別ファイルを取り出せる
（外部ツールの導入は要らない）。**取り出した対訳は、対照表へ入れる前に既知の語（Asset など）で
突き合わせて、資料そのものが正しいことを確かめる。**

**Hub の訳はエディタ UI そのものではない**（Hub と Editor は別プロダクト）。同じ語が Editor で
違う訳になっている可能性は残るので、`.po` を入れられるときは入れて確かめるのが一番強い。
それでも「まったく証拠が無い」状態より確実に良い。

## 対照表を更新するとき

Unity の言語モジュールの `.po`（Unity Hub → Add modules → 言語）を取得し、
`msgid` が語と完全一致するエントリの `msgstr` を数え直す。版を上げたら `unityVersion` も直す。
**Unity 6 で訳が変わっている語がある**（実測: `Asset Store` が 2022.3 の `资源商店` から
Unity 6 で `资产商店` へ反転していた）ので、対象バージョンの `.po` を見ること。
